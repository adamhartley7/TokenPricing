How LLM billing actually works

1. Tokens

Models bill per token (~¾ of a word). You pay separately for input (what you send — prompts, files, conversation history) and output (what the model generates). Output is almost always the pricier side — typically 3–6× the input rate.

2. The cache is the whole game for coding agents

A coding agent re-sends huge context (your files, the running transcript) on every turn. Without caching you'd pay full input price each time. Prompt caching stores that repeated context so subsequent turns read it at a steep discount:

  • Cache write (creating the cache) costs a little more than normal input (~1.25× on Claude).
  • Cache read (reusing it) costs ~10% of the input rate on Claude — and as little as ~2% on DeepSeek.

This is why a usage report can show hundreds of millions of tokens but a modest effective cost: the vast majority are cheap cache reads. It's also why "total tokens" is a misleading cost proxy — the mix matters far more than the total.

3. Flat subscription vs metered API — different axes

A subscription (Claude Max, ChatGPT Plus/Pro) is a flat monthly fee with a rate limit — you buy a capped firehose, not a token bucket, and the providers don't publish exact token quotas. A metered API charges exactly per token with no ceiling. Neither is "cheaper" in the abstract — it depends entirely on volume.

4. Reading a break-even

Convert the flat fee into the token volume that would cost the same at API rates. Above that volume the subscription wins; below it, metering wins. For Claude Opus at $5/$25 per 1M (80/20 blend ≈ $9/1M), $200 buys ≈ 22M tokens/mo of API — a heavy daily agent user passes that in days, so the flat plan wins decisively. The Calculator tab computes this live for your ratio.

5. The routing mindset

The cost-optimal setup is rarely one vendor. Run your premium interactive agent on whatever flat plan you already pay for; push cheap bulk, background and vision work to a low-cost metered key (Gemini Flash-Lite, Qwen-flash, DeepSeek V4 Flash); and consider a local model for privacy or very-high-volume background jobs. Match each task to the cheapest tool that's good enough.

Running models locally with Ollama

Ollama is a free, open-source tool that runs open-weight models on your own machine. Marginal cost per token is ~$0 — you pay only electricity and the up-front (amortized) hardware. It serves an OpenAI-compatible endpoint at http://localhost:11434/v1, so any tool that speaks the OpenAI API — coding agents, IDE extensions — can point at a local model as a drop-in substitute.

ollama pull qwen3-coder then ollama run qwen3-coder. Models are quantized GGUF files (default Q4_K_M — a good size/quality balance). Commonly run: Qwen / Qwen3-Coder, Llama, DeepSeek-R1 distillations, and OpenAI's open-weight gpt-oss.

The trade-offs (honest)

  • Quality: what fits on a single consumer GPU (≤~32B) trails flagship cloud models. SWE-bench: Opus 4.8 ≈ 88.6% vs the best you'll realistically self-host being well below that.
  • Speed: fine for chat; a coding agent's heavy prompt-prefill is slower and bigger models crawl on small VRAM.
  • Tool-use reliability: agentic loops depend on solid function-calling — verify on your real tasks before trusting a local model for it.
  • Cost shape: local is cheapest per token at very high sustained volume (amortized hardware divides across many tokens) and poor value at low volume, where a metered API or a plan you already own wins.

VRAM → model-size guide

Rule of thumb: VRAM_GB ≈ params_B × bytes_per_param × 1.2; bytes/param ≈ 0.5 (Q4_K_M), 1.0 (Q8), 2.0 (FP16). Add 1–4 GB for long context.

Model sizeQ4_K_MPractical fit
7–8B~5–7 GB8 GB GPU runs this comfortably
13–14B~10–12 GB12 GB GPU; 16 GB for Q8
32–34B (incl. Qwen3.6-27B)~21–23 GB24 GB (RTX 3090/4090) runs this well
70B~40–46 GBneeds 48 GB / 2×24 GB

Apple Silicon (unified memory): 16 GB → 7–8B; 32 GB → ~32B Q4; 64 GB → 70B Q4. Old Intel Macs are CPU-only — not recommended (~3–5 tok/s on 7B). Thin-and-light laptops (Core Ultra NPU / iGPU): realistic ceiling ~7–8B Q4; 32B+ not feasible. NAS / Time-Capsule-type devices are storage, not compute — they can hold model files but can't run them.

Auto-updating usage — the safe way

You cannot link a Claude/Gemini/OpenAI account to a static web page, and you must never put an API key in a public page (anyone can read it via Inspect Element — Google's own docs say "Do not hardcode API keys directly in web or mobile apps … run a backend proxy"). The safe pattern keeps everything on your machine:

  1. Run sync-usage.ps1 (in this repo). It runs npx ccusage@latest monthly --json locally and writes usage.json beside this page.
  2. This page fetch()es usage.json and profile.local.json at load and prefills automatically. Both files are git-ignored and never published; nothing is transmitted anywhere.
  3. For personalization, copy profile.local.example.json → profile.local.json and fill in your role / location / devices.
# Windows PowerShell, in the repo folder
./sync-usage.ps1
# → writes usage.json (local only). Reload the page.

Official Anthropic-compatible endpoint. Tool-use reliability with non-Anthropic models can differ from native Claude — test your agentic loops before relying on it.

$env:ANTHROPIC_BASE_URL="https://api.deepseek.com/anthropic"
$env:ANTHROPIC_AUTH_TOKEN="<your-deepseek-key>"
$env:ANTHROPIC_MODEL="deepseek-v4-pro"
$env:ANTHROPIC_DEFAULT_HAIKU_MODEL="deepseek-v4-flash"
claude

Multi-provider alternative (also fronts OpenAI/Gemini/Qwen/local): npm i -g @musistudio/claude-code-router then ccr code. For local models, point any OpenAI-compatible client at http://localhost:11434/v1.

Why no API keys in the page

A static site has no server to hide a secret. Any key in client-side JS is downloadable by every visitor and extractable from the browser. To call a paid API from a web app safely, put the key behind your own backend proxy that the page calls — the key never reaches the browser. For this calculator, no key is needed at all: it only does arithmetic on token counts you provide.
